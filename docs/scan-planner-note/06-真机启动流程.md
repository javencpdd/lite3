# 真机启动操作单（SCAN-Planner × Lite3 × Livox Mid360）

> 适用：103 主机（`/home/test/scan_planner`），首次真机联调。
> 前置结论：**雷达是 Livox Mid360**，走 ROS1 的 `start_livox.sh`（见 `05-避坑事项.md` 第 11 章）。
> 最后更新：2026-09-25

## 0. 总览：开几个终端、各干什么

| # | 终端 | 干什么 | 能否合在一起 |
|---|---|---|---|
| T1 | 本体链路 / IMU | `start_transfer.sh`（**顺带把 roscore 拉起来**） | 不能，必须最先 |
| T2 | 雷达 | ROS1 `start_livox.sh` | 不能 |
| T3 | SLAM | `start_slam.sh` → faster_lio | 不能 |
| T4 | 话题适配 | `scripts/start_lio_relay.sh` | 不能 |
| T5 | 规划器 | `scripts/start_scan_real.sh` | 不能 |
| T6 | 监控 / 下发目标 | `rostopic` 检查 + `scripts/goal.sh` | 可以和 T7 合 |
| T7 | ROS1↔ROS2 桥 | `ros1_bridge parameter_bridge` | **最后一步，且先不接机器人** |

**最少 6 个终端**（T7 桥接可以等确认无误后再开）。

> ⚠️ 每个终端开工第一件事都是**建环境**，见第 1 节。
> T1/T2/T3 跑的是 ysc 自带的脚本（它们内部会 source 自己的 workspace），
> 但**先 `source scripts/env.sh` 无害且更稳** —— 能保证 `roslaunch` 存在、master 地址一致。

## 1. 建环境（每个终端都要做，第一件事）

103 的 `~/.bashrc` 默认加载 **ROS2 foxy**，而 foxy **没有 `roslaunch`**（只有 `ros2 launch`）。
不建环境的典型症状：`bash: roslaunch: command not found`。

```bash
cd /home/test/scan_planner
source scripts/env.sh
```

正常输出（**两行都要看到**）：

```
[env] 原环境已快照 -> logs/env_backup_0925_010000_12345.sh
[env] ROS_DISTRO=noetic  AMENT=[empty]
[env] ROS_MASTER_URI=http://192.168.1.103:11311  ROS_HOSTNAME=192.168.1.103
```

自检（可选）：

```bash
which roslaunch        # 应为 /opt/ros/noetic/bin/roslaunch
echo $ROS_MASTER_URI   # 必须和 SLAM 那侧一致, 不要是 localhost
```

收工时复原（会精确还原，包括"原本没设"的变量）：

```bash
source scripts/env_restore.sh
```

## 2. T1：本体链路 / IMU（**必须第一个开**）—— ⚠️ 有坑，先读 2.1

```bash
cd /home/test/scan_planner && source scripts/env.sh
bash /home/ysc/lite_cog/system/scripts/transfer/start_transfer.sh
```

### 2.1 🔴 ROS1 / ROS2 两套 transfer **抢同一个 UDP 端口 43897，互斥**

**实测现象**：ROS1 侧 `/imu/data`、`/joint_states`、`/leg_odom`、`/leg_odom2` **全都没流**，
`/sensor_status/imu_isalive = False`，而 ROS2 侧 `/imu/data` **200 Hz 正常**。
于是 ROS1 的 faster_lio 收不到 IMU → `/Odometry`、`/cloud_registered_body` 永远 `no new messages`。

**根因**：两套 transfer 都绑 `0.0.0.0:43897` 收机器人遥测：

| 栈 | 文件 | 端口 |
|---|---|---|
| ROS1 | `transfer/src/message_transformer/src/qnx2ros.cpp` → `server_port` | **43897** |
| ROS2 | `lite_cog_ros2/transfer/src/transfer/src/Jetson2Motion.cpp` → `local_port` | **43897** |

`transfer_ros2.service` 开机就起（22:45，systemd 常驻），**先占了 43897**；
后来起的 ROS1 `qnx2ros` 的 `bind()` 失败，而代码只 `perror("bind error:")` 不退出 ——
**节点活着、话题在、但一条数据都没有**。回看终端能看到 `bind error: Address already in use`。

**必须二选一：**

**方案 A（推荐，本次联调）—— 让 ROS1 链路接管，全程不用 bridge**

```bash
sudo systemctl stop transfer_ros2.service     # 让出 43897
# 回到 T1 终端 Ctrl+C 掉刚才那个（bind 已失败, 状态是坏的）
pkill -f "message_transforme[r]"              # 或用 T1 的 Ctrl+C
bash /home/ysc/lite_cog/system/scripts/transfer/start_transfer.sh
```

确认：`rostopic hz /imu/data` → 期望 ~200 Hz，`/sensor_status/imu_isalive` → True。

好处：命令回传也是纯 ROS1（ROS1 `ros2qnx` 订阅 `/cmd_vel` → 120:43893 → 机器人），
第 ⑧ 步连 ros1_bridge 都不需要，只要一条 `topic_tools relay`（见第 8 节）。
代价：测试期间 ROS2 侧链路（nav2 等）停用。测完 `sudo systemctl start transfer_ros2.service` 恢复。

**方案 B —— 不动常驻服务，把 IMU 桥进 ROS1**

```bash
source /opt/ros/noetic/setup.bash
source /opt/ros/foxy/setup.bash
ros2 run ros1_bridge parameter_bridge /imu/data@sensor_msgs/msg/Imu@sensor_msgs/Imu
```

保持 `transfer_ros2.service` 运行，命令侧仍按原计划桥 `/scan_planner/cmd_vel` → ROS2 `/cmd_vel`。
代价：**两条桥**，且 ros1_bridge 在 103 上还没实测过。.sh
```

作用：起 `message_transformer`（`ros2qnx` / `nx2app` / `sensor_checker`），
发布 FAST-LIO 需要的 **`/imu/data`**（机器人本体 IMU，**不是雷达的** `/livox/imu`）。
它内部 `roslaunch` 会**自动把 roscore 拉起来**，所以 T2～T5 才有 master 可连。

确认：

```bash
rostopic hz /imu/data      # 期望 ~200 Hz（本体 IMU）
```

> 若已在跑（见 `ps aux | grep message_transformer`），**不要重复起**，会抢端口。

## 3. T2：雷达（Livox Mid360）

```bash
cd /home/test/scan_planner && source scripts/env.sh
cd /home/ysc/lite_cog/system/scripts/lidar
bash start_livox.sh
```

⛔ **不要跑** `start_lslidar.sh`（镭神 C16 驱动，硬件对不上）；
⛔ **不要跑** `lite_cog_ros2/system/scripts/lidar/` 下的任何脚本（ROS2 栈，FAST-LIO 收不到）；
⛔ **同一时刻只能起一个雷达驱动**（两份 livox 驱动都绑 `:56301`/`:56401`，必冲突）。

确认（注意点云名**被 remap 过**，没有 `/livox/lidar`）：

```bash
rostopic hz /rslidar_points    # 期望 ~10 Hz
rostopic echo /rslidar_points -n1 | head -30    # 看 fields 布局, 顺手记下来
```

期望输出关键行：

```
[INFO] [livox_lidar_publisher2-1]: [driver][socket] Opening UDP socket: port 56301
```

若刷 `[driver][socket] incomplete lslidar packet read: 60 bytes` → 说明**起错驱动了**。

## 4. T3：SLAM（faster_lio）

**有桌面会话时**（103 上 `who` 能看到 `:0`）：

```bash
cd /home/ysc/lite_cog/system/scripts/slam
bash start_slam.sh
```

它会开三个 gnome-terminal：faster_lio、`gridmap.sh`（输 1 才建图）、`save_map.sh`（输 2 才存图）。

**⚠️ 纯 SSH（没有 DISPLAY）时 `start_slam.sh` 必然失败**，报：

```
Unable to init server: Could not connect: Connection refused
Failed to parse arguments: Cannot open display:
```

原因有两个，**都得绕开**：

1. `start_slam.sh` 用 `gnome-terminal -x` 开三个窗口，无 X 就起不来；
2. `mapping_c16.launch` 里 `<arg name="rviz" default="true" />`，
   即使绕开 gnome-terminal，rviz 在 headless 下也起不来 → **必须显式 `rviz:=false`**。

推荐直接用封装脚本（已处理这两点）：

```bash
cd /home/test/scan_planner && source scripts/env.sh
bash scripts/start_slam_headless.sh
```

等价手动版：

```bash
cd /home/test/scan_planner && source scripts/env.sh
source /home/ysc/lite_cog/slam/devel/setup.bash
roslaunch faster_lio mapping_c16.launch rviz:=false
```

> `start_slam.sh` 另外两个 gnome-terminal（`gridmap.sh` / `save_map.sh`，靠交互输入 1 / 2）
> 是给 **nav2 建/存栅格地图**用的，**SCAN-Planner 不需要**（它自己建 occupancy grid）。
> 真要建图就单独跑 `bash /home/ysc/lite_cog/system/scripts/slam/gridmap.sh` 然后输入 `1`。

确认：

```bash
rostopic hz /Odometry                  # 期望 ~10~20 Hz
rostopic hz /cloud_registered_body     # 机体系点云, relay 要用这个
rostopic echo /Odometry -n1 | head -12 # 确认 frame_id: camera_init -> body
```

> `mapping_c16.launch` 里的 `c16` 是历史遗留，它吃的就是 remap 后的 Mid360 点云，**不用改**。
> 如果报"点云为空/无有效点"，见第 9 节排障表。

## 6. T5：SCAN-Planner（真机模式，先不接机器人）

```bash
cd /home/test/scan_planner && source scripts/env.sh
bash scripts/start_scan_real.sh
```

等价于：

```bash
roslaunch scan_planner run.launch \
  is_real_world:=true navi_mode:=1 sensor_type:=lidar need_extrinsic:=false
```

两道安全设计（已在脚本/launch 里固化，别去掉）：

- `need_extrinsic:=false` —— 否则会叠 Go2 的雷达外参（点云已经是机体系了）
- 输出被 remap 到 **`/scan_planner/cmd_vel`**，**绝不碰**机器人正在消费的裸 `/cmd_vel`

确认：

```bash
rostopic hz /grid_map/occupancy     # 期望 ~20 Hz, 地图在滚
rostopic list | grep cmd_vel        # 应只有 /scan_planner/cmd_vel
rostopic info /cmd_vel | head -5    # 裸 /cmd_vel 必须没有任何 scan_planner 发布者
```

## 7. T6：下发目标点（先小范围！）

```bash
cd /home/test/scan_planner && source scripts/env.sh
bash scripts/goal.sh 2.0 0.0 0.3      # 先给 2 米, 别一上来 5 米
```

（默认值是 `(5.0, 0.0, 0.3)`；`navi_mode=1` 订阅 `/move_base_simple/goal`，rviz 的 2D Nav Goal 同样有效。）

下发后观察 T5 日志：

```
[FSM] INIT -> WAIT_TARGET -> GEN_NEW_TRAJ -> EXEC_TRAJ
```

以及 `/planning/bspline`、`/scan_planner/cmd_vel` 开始出数据。

> ⚠️ **不要在测量窗口里跑 `rostopic hz` / `echo` / `rosparam get`**！
> 6 核 Jetson 上并发探测会把 `pcl_render_node` 拖慢，导致规划器"以为"自己在障碍里
> （曾出现 a* error 1139 / Replan failed 1000 的**伪故障**，复现干净时只有 616 行日志）。
> 判读请等一轮跑完再看日志。

## 8. T7：回传速度指令（**最后一步，慎开**）

**若走方案 A（ROS1 接管本体链路）**：命令通路是纯 ROS1，
`ros2qnx` 订阅 ROS1 `/cmd_vel` → 120:43893 → 机器人，**不需要 ros1_bridge**：

```bash
cd /home/test/scan_planner && source scripts/env.sh
rosrun topic_tools relay /scan_planner/cmd_vel /cmd_vel
```

**若走方案 B（保留 ROS2 常驻服务）**：需要 ros1_bridge（**最后一步，未实测**）

只桥 **一条** `/cmd_vel`，点云和里程计原生同域，不要用 `dynamic_bridge` 全量桥。

```bash
source /opt/ros/noetic/setup.bash     # 先 ROS1
source /opt/ros/foxy/setup.bash       # 再 ROS2
ros2 run ros1_bridge parameter_bridge \
  /scan_planner/cmd_vel@geometry_msgs/msg/Twist@geometry_msgs/Twist
```

⚠️ 这一步**本机还没实测过**。建议顺序：

1. 先**不开桥**，跑几轮看 `/scan_planner/cmd_vel` 数值是否合理（速度 ≤ 0.75 m/s）；
2. **四腿离地**（把狗架起来）再开桥，看轮子/腿是否按预期响应；
3. 确认无误后再落地。

## 9. 排障速查

| 现象 | 原因 | 处置 |
|---|---|---|
| `roslaunch: command not found` | 终端默认 foxy | `source scripts/env.sh` |
| `incomplete lslidar packet read: 60 bytes` | 起错驱动（lslidar） | 换 `start_livox.sh` |
| `/rslidar_points` 无数据 | 雷达没上电 / 驱动抢端口 | 确认只起了一个驱动；`ip neigh` 看 `.201` 在不在 |
| `/imu/data` 无数据 | T1 没起 | `bash start_transfer.sh` |
| relay 报"连不上 master" | T1 没起或 master 地址不一致 | 检查 `ROS_MASTER_URI` 两边都是 `192.168.1.103:11311` |
| FASTER-LIO 报点云为空 | PointCloud2 fields 布局不匹配 | 见下 |
| 规划器狂刷 a* error / Replan failed | ① 真的被围住 ② **并发探测导致的伪故障** | 停掉所有 `rostopic hz`，用 `ab_test.sh` 复跑两次再下结论 |
| 机器人突然动起来 | 裸 `/cmd_vel` 被发布 | 确认 `robot_pkg` 用的是带 remap 的 `run.launch` |

**点云 fields 不匹配**（Livox vs 镭神 C16）的排查：

```bash
rostopic echo /rslidar_points -n1 | sed -n '1,25p'
```

| 来源 | fields |
|---|---|
| Livox Mid360 | `x, y, z, intensity, tag, time` |
| 镭神 C16 | `x, y, z, intensity, ring, timestamp` |

若 FAST-LIO 的 `lidar_type: 4` 分支读的字段名对不上，去查
`/home/ysc/lite_cog/slam/src/faster-lio/src/preprocess.cpp` 里 `lidar_type==4` 的处理。

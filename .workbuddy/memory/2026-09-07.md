## YOLO26n 选型评估（补充）

用户质疑为何方案未纳入 YOLO26n。做了专项调研并沉淀为方案文档 4.4 节。

**核心结论**：
- **决定性证据**：Ultralytics `end2end-detection` 指南明确，RKNN/NCNN/ExecuTorch/Edge TPU 等格式会 **fallback 到一对多头（仍需 NMS）**。因此形态 B（RK3588+RKNN）上 YOLO26 的 NMS-free 优势归零 → 形态 B 明确不切。
- 形态 A（Jetson GPU）：T4 TensorRT 上 YOLO26n 1.7ms **慢于** YOLOv8n 1.47ms；社区在 Jetson Orin Nano 4GB 上实测 YOLO26 默认导出为 1x84x8400（缺端到端子图），有 bbox 漂移与置信度不准，作者回退到 v8n → 暂不切换但纳入并行验证。
- YOLO26 的真实优势是 **CPU/无 GPU 场景（ONNX 38.9ms vs 80.4ms，快 51%）** 和 **STAL 小目标召回**，但本项目 L1 已承担小目标召回，边际价值被削弱。
- 训练约束：不能沿用 v8 超参（小数据集 lr×0.7、骨干 lr 低于检测头）、一对一分配禁强增广（弱化 mosaic、关随机透视）——本项目仅 200~500 张，配错反而掉点。
- 许可证两者同为 AGPL-3.0，**无差异**（不是决策变量）。
- Python 3.8：官方 >=3.8（v8.3.61 起恢复兼容），103 不阻断。

**切换门限（4 条须全满足）**：导出为 (1,300,6) 无漂移 / 小目标召回提升 ≥5pp / 误报率不劣化 / 103 端到端时延劣化 ≤10%。

**最小实验**：同数据集各训 1 次 100 epoch → 导出 go/no-go（先看 shape 是否 fallback）→ 103 实机 60s 视频对比 → 按门限决策。RKNN 导出必须在 x86 Linux 上做（不支持 ARM64）。
